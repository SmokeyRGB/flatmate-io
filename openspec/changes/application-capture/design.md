## Context

See proposal.md, Why. The state this design builds on (verified 2026-09-28 on `main` `43d2f49`):

- **`application`** (`casting/schema.ts`) has only lifecycle columns, a nullable `round_id` and
  `deleted_at`. Two policies apply: the permissive household policy, and RESTRICTIVE
  `application_requires_resident_profile` (`drizzle/0018`, G-D15). Dev holds **0** `application`
  rows. There are no foreign keys anywhere.
- **Permission check.** `assertHasPermission` (`identity/repository.ts`) reads the membership in
  its own transaction (`getMembershipForAccount`) and then returns. The caller's write runs in a
  second transaction. `household_admin` passes every check. `MODERATOR_DEFAULT_PERMISSIONS` is
  `{manage_rooms, close_round}`.
- **Who writes `casting_round.status` today:** only `openRoundTx` (`draft → open`, under
  `FOR UPDATE`). A close or pause does not exist yet.
- **Who writes `membership`:** `revokeMembershipForProfileTx` (removal and move-out),
  `reactivateMember`, `setMemberRole`, and registration or claim inserts. All are plain `UPDATE`s
  or `INSERT`s, so each takes the row lock.
- **Audit.** `recordActivityEvent` validates the payload against `PAYLOAD_ALLOWLIST`, and an
  unregistered type throws.
- **UI.** `rounds/new` is the form precedent: a `useActionState` action returning `{ error }`, and
  a page guard via `assertHasPermission` + `PermissionDeniedError`. `SubmitButton`, `SuccessToast`,
  the `JoinCodeCopyButtons` copy pattern and the `skeletons` exist. There is no `(org)/error.tsx`.
- **Tests.** 7 files insert `application` rows directly (Drizzle and raw SQL), 3 of them without
  any round. Page-render tests use `renderToStaticMarkup` with mocked modules
  (`tests/unit/casting/new-round-page-permission-guard.test.ts`).
- **Change 1's gate.** Every `schema.ts` column needs a `data-inventory.yml` entry. The live test
  is strict only on CI's repo-built DB. `ART9_BLOCKLIST`/`matchArt9Term` are exported from
  `scripts/lint/data-inventory.ts`.

## Goals / Non-Goals

**Goals:**
- Every rule of `specs/casting/application-capture` is enforced in the repository, where
  applicable in the database too, and not only in the route.
- Enforce the two relationships this change starts relying on (membership ↔ admin profile, and a
  capture's round ↔ household) in the database, for every writer.
- Keep typed applicant data out of server responses and logs.

**Non-Goals:**
- The pipeline list, editing, the Art. 13 notice for every application, and the
  `transitionApplication` guard: change 3.
- Deletion, tombstones, dropping `deleted_at` and `REDACTABLE_KEYS` for `application.created`:
  change 4. `deleted_at` stays in `schema.ts` and is never written here.
- V-2 row visibility: change 6.
- A route-group guard on `(org)`. **Found while planning:** `src/app/(org)/layout.tsx` checks only
  that someone is signed in. A plain member sees no link to the organisation pages
  (`getNavigationAccess`), but a typed `/organization` or `/rounds/[id]` still renders O1 and the
  round page, participant names included. No application data is exposed there: this change's two
  new routes refuse on their own, and so does every repository function behind them. The
  layout-level guard belongs to change 5, which rebuilds O1 and decides who O1 is for (a member
  granted one permission is a legitimate organisation user).
- Closing the permission/write window in the *other* existing mutators (rooms, rounds, settings).
  They keep their two-transaction shape. See Risks.

## Decisions

### D1 — Migration `0023_application_capture.sql`: shape and statement order

Generated by `drizzle-kit generate` from `schema.ts` (so the snapshot and journal stay drizzle's),
then hand-edited for re-runnability (`migration-shape.ts` applies to files after 0017). Order, with
the constraints live at each statement:

1. `LOCK TABLE application IN ACCESS EXCLUSIVE MODE;`. From here on, no concurrent test insert can
   land between the precondition check and the `ALTER`s. The `ALTER`s would take this lock anyway,
   but only *after* the check.
2. Precondition, a `DO $$ … $$` block. **If** the column `applicant_name` does not exist yet
   **and** any `application` row exists, then `RAISE EXCEPTION` naming the count and the reason
   (NOT NULL columns without a default, and no invented names). The column-exists guard keeps a
   later full re-run from failing on rows that legitimately exist by then. This subsumes the plan's
   "no `round_id IS NULL` rows" precondition, since any row blocks. Applied migrations run as
   `postgres`, which RLS does not filter, so the count is real.
3. `CREATE TYPE application_source …` and `application_collected_from …`, each wrapped
   `DO $$ BEGIN … EXCEPTION WHEN duplicate_object THEN NULL; END $$;`. They are new types, not
   `ADD VALUE`, so rule 1 (the own-file rule) does not apply.
4. `ADD COLUMN IF NOT EXISTS`, each on its own statement: `applicant_name text NOT NULL`, `age
   integer`, `contact_email text`, `contact_phone text`, `contact_other text`, `message_raw text`,
   `attributes jsonb`, `source application_source NOT NULL`, `collected_from
   application_collected_from NOT NULL`. **No `DEFAULT`** on any of them (C-3.2, AC-3.7). They are
   valid only because step 2 proved the table empty. Nothing else is live on these columns yet.
5. `ALTER COLUMN round_id SET NOT NULL`. Re-runnable as written, and valid on the empty table.
6. The CHECKs, each `DROP CONSTRAINT IF EXISTS` then `ADD CONSTRAINT` (re-runnable, the 0020
   precedent):
   - `application_applicant_name_length`: `char_length(btrim(applicant_name)) BETWEEN 1 AND 200`,
     plus `application_applicant_name_not_blank`: `applicant_name ~ '[^[:space:]]'`. `btrim` strips
     spaces only, so without the second CHECK a name of tabs, line breaks or NBSP would pass the
     database (pre-mortem 9). The parser's rule (D4) is at least as strict: JavaScript `trim()` plus
     the same "one non-whitespace character" test.
   - `application_contact_email_length` (≤ 254), `…_contact_phone_length` (≤ 50),
     `…_contact_other_length` (≤ 200), `…_message_raw_length` (≤ 4000). Each is
     `x IS NULL OR char_length(x) <= n`.
   - `application_age_range`: `age IS NULL OR age BETWEEN 0 AND 150`.
   - `application_attributes_shape`: `attributes IS NULL OR CASE WHEN jsonb_typeof(attributes) =
     'array' THEN jsonb_array_length(attributes) BETWEEN 1 AND 10 ELSE false END`. The `CASE` matters:
     `jsonb_array_length('{}')` raises `22023` instead of a check violation, and `AND` gives no
     evaluation-order guarantee (pre-mortem 15). **Per-element limits (label/value
     lengths and the object shape) are enforced in the repository only.** A CHECK cannot contain a
     subquery, and a trigger for this is not worth its weight. This is named in the spec and in
     the schema comment, so nobody believes the CHECK covers it.
   - Order among the CHECKs doesn't matter, because the table is empty.

7. **The round pairing trigger** (D12): `CREATE OR REPLACE FUNCTION
   application_round_same_household() RETURNS trigger`, then `DROP TRIGGER IF EXISTS` + `CREATE
   TRIGGER application_round_same_household BEFORE INSERT OR UPDATE OF round_id, household_id ON
   application FOR EACH ROW`. It comes last, after `round_id` is NOT NULL, and the table is still
   empty, so no existing row is checked retroactively; none exists anyway.

`btrim` counts after trimming, and the repository also stores the trimmed name (D4), so both agree.
`char_length` counts code points, which is why the browser counter counts code points too (D6).

*Alternative rejected:* adding the columns nullable, backfilling, then `SET NOT NULL`. There is
nothing honest to backfill a name or a collection source with. C-3.2 forbids exactly that
("never silently defaulted").

`schema.ts` mirrors all of it. The two `pgEnum`s are allowed in `schema.ts` (change 1's handover).
The CHECKs go in via drizzle's `check()`, as `identity/schema.ts` already does, and the comments
cite C-3.14. **drizzle-kit keeps only the SQL text of a `check()` and drops its bound parameters**
(`dialect.sqlToQuery(check.value).sql`, `node_modules/drizzle-kit/bin.cjs:16268`). So every value
inside a `check()` is written with `sql.raw` or as literal SQL, never interpolated as `${value}`.
Otherwise the migration contains `$1` and fails. After each `generate`, the applier greps the new
file for `$` outside the `DO $$` blocks (pre-mortem 3).

### D2 — Migration `0024_membership_role_integrity.sql`

Mirrored with `check()` in `identity/schema.ts`. It starts with `LOCK TABLE membership IN SHARE ROW
EXCLUSIVE MODE`, so no registration, claim, role change, move-out or reactivation can land between
a backfill and the CHECK that relies on it (pre-mortem 6). Then, ordered by the constraints live at
each statement:

1. `membership_admin_has_no_profile`: `CHECK (role <> 'household_admin' OR resident_profile_id IS
   NULL)`. It stands alone, and dev holds 0 violating rows (checked 2026-09-28).
2. **Backfills**, each idempotent, so a re-run touches nothing:
   - a. revoked rows: `SET role = 'member', permissions = '{}' WHERE revoked_at IS NOT NULL AND
     (role = 'moderator' OR cardinality(permissions) > 0)`. A moved-out person keeps nothing (D3);
   - b. live moderators: `permissions = ARRAY(SELECT DISTINCT unnest(permissions || <MOD>) ORDER BY
     1)` where the set is missing. This drops no stored value;
   - c. the live administering membership: `permissions = <HOUSEHOLD>` outright (the set is exact,
     step 3);
   - d. live residents: the union with `<RESIDENT>`. It is a no-op while that set is empty, and is
     kept so F4's widening is a one-line change.

   Dev holds 1 moderator and 1 administering row, both with `[]` (checked 2026-09-28). The applier
   records the revoked rows before applying. It runs as `postgres`, so RLS does not hide rows.
3. The role CHECKs, each `DROP CONSTRAINT IF EXISTS` + `ADD`, valid only after step 2:
   - `membership_moderator_holds_role_permissions`: `revoked_at IS NOT NULL OR role <> 'moderator'
     OR permissions @> <MOD>`;
   - `membership_household_admin_holds_role_permissions`: `revoked_at IS NOT NULL OR role <>
     'household_admin' OR (permissions @> <HOUSEHOLD> AND permissions <@ <HOUSEHOLD>)`. The set is
     **exact**, because the matrix gives the household account no ⬜;
   - `membership_resident_holds_role_permissions`: `revoked_at IS NOT NULL OR NOT is_resident OR
     permissions @> <RESIDENT>`;
   - `membership_revoked_holds_nothing`: `revoked_at IS NULL OR (cardinality(permissions) = 0 AND
     role <> 'moderator')`.

In `schema.ts` the CHECKs are built **from the exported constants** `HOUSEHOLD_PERMISSIONS`,
`RESIDENT_PERMISSIONS` and `MODERATOR_PERMISSIONS` (plain values, which `schema.ts` may export, per
change 1's rule), so a constant and its constraint cannot drift. The array literal is produced with
`sql.raw` from the constant (each value single-quote-escaped, and `'{}'::text[]` for an empty set),
never as a bound parameter, because drizzle-kit would write `$1` (D1, pre-mortem 3).

**Why the admin/profile CHECK.** This is ADR-013 (the account type is fixed), and it is now
load-bearing. It keeps the household role and the resident role from ever landing on the same
membership, so the household set never mixes with the resident's or moderator's.

**Why the role CHECKs.** D3 makes the stored permissions the only thing a check reads. A
membership that disagrees with its roles would silently gain or lose rights. The CHECKs turn that
into a refused write, for every writer, including raw SQL and tests that set a role directly. Two
tests set `role: 'moderator'` directly (`join-code-isolation.test.ts`, `resident-list-access.test.ts`)
and move to `setMemberRole`. One test inserts a `household_admin` row with `permissions: []`
(`tests/unit/identity/provider-user-compensation.test.ts`) and gets the set. All three are setup
changes only, and none is guarded.

### D3 — Roles are names for permission sets (human decisions 2026-09-28 and 2026-09-29)

*"The terms 'household' or 'moderator' should simply map to permissions; they shouldn't be a
separate workaround for permissions / Backdoor for ignoring permissions."* And: *"Permissions are
granted via becoming/occupying one of the roles (resident, moderator, household) and revoked when
someone looses the moderator role / moves out and looses the resident status."*

So there is **one** rights mechanism, stored permissions. A role is only a name for a fixed set,
and a membership holds the union of the sets of the roles it occupies. Until now
`assertHasPermission` answered `true` for any `household_admin`, and for a moderator whenever the
permission was in `MODERATOR_DEFAULT_PERMISSIONS`, whatever `membership.permissions` held. That is
replaced as follows:

- **Three constants in `identity/schema.ts`**, one per role (`domain/identity.md` §2.1 calls them
  *„vorbelegt"*, and storing them is the literal reading of that word):

  | Role | Occupied by | Constant |
  |---|---|---|
  | household | `role = household_admin` (never with a profile, D2) | `HOUSEHOLD_PERMISSIONS` = `manage_rooms`, `manage_settings`. **Not `close_round`**: the matrix gives the household account ❌ for rounds (D13) |
  | resident | a live membership with `is_resident` | `RESIDENT_PERMISSIONS` = empty in this change. The matrix's resident ✅ actions (voting, veto, notes, availability) aren't built yet, and F4's `vote` is the first |
  | moderator | `role = moderator` | `MODERATOR_PERMISSIONS` = `manage_rooms`, `close_round`, `create_application`, `change_application_state` |

- **`membershipHoldsPermission(row, permission)`**, one pure exported function:
  `row.revokedAt === null && row.permissions.includes(permission)`. **No role is read.** It is used
  by `assertHasPermission` and by the transaction-scoped check (D4), so the rule exists in exactly
  one place. (`getMembershipForAccount` already filters revoked rows. The `revokedAt` test makes the
  pure function correct on its own.)
- **Every writer of `role`, `permissions`, `is_resident` or `revoked_at`** keeps them consistent, in
  **one statement on one row**, so the pairs serialize on the row lock. The unions and differences
  are computed **in SQL inside the `UPDATE`** (`ARRAY(SELECT DISTINCT unnest(permissions || …))`,
  and `array(select unnest(permissions) except select unnest(…))`), never in JS from an earlier
  unlocked read (pre-mortem 11):
  - `registerHousehold` inserts the administering membership with `HOUSEHOLD_PERMISSIONS`. Its undo
    deletes the row.
  - Claim and join insert a resident membership with `RESIDENT_PERMISSIONS`.
  - `setMemberRole` → moderator: `∪ MODERATOR_PERMISSIONS`; → member: `− MODERATOR_PERMISSIONS`,
    then `∪ RESIDENT_PERMISSIONS` for a resident. So a permission in both sets survives demotion
    (none today, but F4's `vote` must not be lost by demoting a resident moderator). The event stays
    `membership.role_changed` `[fromRole, toRole]`.
  - `revokeMembershipForProfileTx` (move-out and removal) sets `revoked_at`, `role = 'member'` and
    `permissions = '{}'` in the one `UPDATE` it already runs. The events stay `membership.revoked` /
    `membership.removed_as_intruder`, and losing the moderator role is part of the revocation, with
    no separate event. The `isNull(revokedAt)` guard on that `UPDATE` stays: a second revocation
    (moved out, then removed) finds nothing left to clear.
  - `reactivateMember` clears `revoked_at` and sets `permissions = RESIDENT_PERMISSIONS`, as a
    `member`. A former moderator is appointed again, visibly, rather than silently regaining the
    role.
  - The applier searches for any other writer and reports the list.
- **Individual grants (the matrix's ⬜)** stay possible in the model, as extra stored values beyond
  the role sets. No function writes one. If a grant screen is ever built, it must decide how
  demotion and revocation treat a grant that overlaps a set.
- **Role checks that are not permission checks** (the ~28 `assertIsAdministration` /
  `assertIsAdministrationOrModerator` / `role ===` sites in identity) become permissions in change 2b
  (human decision 2026-09-28). This change builds no new role check: delete and reverse are changes
  3/4, after 2b.

**Finding 1:** the abandonment condition change 0 wrote into `domain/identity.md` §2.1 counts
defaults („eine **fünfte** Rolle-Vorbelegung … ist ein Vorlagensystem"). That would force an S-04
decision in F5 for `confirm_appointment`, which the matrix (precedence 3) already gives the
moderator with ✅. Task 8.3 corrects it to key on the source, and states the three roles as stored
sets.

### D13 — The household account stops running rounds (S-50, human decision 2026-09-28)

`03-PRD.md` §4.0.1 gives the household account **❌** for *„`CastingRound` anlegen / schließen /
wiedereröffnen"* and *„`RoundParticipation` hinzufügen / entfernen"* (S-50/U-20). Until now
`close_round` passed for it through the implicit "every permission". `rounds/new` let it open a
round, O1 offered it the button, and the demo seed opened its round as the household account.
Leaving `close_round` out of `HOUSEHOLD_PERMISSIONS` fixes that. The consequences are:

- **Repository:** nothing to change. `createRound`, `openRound`, `createAndOpenRound`,
  `addResidentToRound` and `listOrganisationTasks` already check `close_round`, and now refuse
  (or return `[]`) for the household account.
- **UI:** `/organization` renders the „Runde eröffnen" button and link only to a session holding
  `close_round` (the same try/catch pattern). `/rounds/new` already shows its permission state.
  The applier searches `src/app` for every other link to `/rounds/new` or round actions and applies
  the same rule. The household account's texts must not promise round creation; the applier checks
  its O20 landing and O1 copy for it.
- **Seed:** the demo round is created and opened as Alex, the moderator. The rooms stay created by
  the household account (`manage_rooms` ✅).
- **Tests:**
  - Every test that creates, opens or adds to a round **with the household context** moves that
    setup to a moderator. A helper `createTestModerator(hh)` in `tests/helpers/identity.ts` claims a
    profile, appoints it through `setMemberRole`, and returns its `SessionContext`.
  - About 17 files use round creation. Two of them are guarded G-D15 files
    (`tests/integration/{policy,raw-sql}/round-visibility-household-account.test.ts`). For those
    two it is a **setup change only**; their assertions about what the household account *sees*
    are unchanged (G-G1, the diff goes to the human).
  - A test that asserts the household account **may** open a round (for example in
    `room-round-authorization.test.ts` or the authorization matrix) states behaviour this change
    deliberately reverses. It is rewritten to assert the refusal, and listed separately in the
    report with the matrix line quoted. That is a spec change, not a weakened test.
- **Other specs:** `openspec/specs/identity/permissions` is replaced by this change's delta. Any
  other current spec sentence saying the household account opens rounds is found by the applier,
  and the archive updates it.
- **Register:** one row closing the contradiction (German, in `docs/review-log.md`).
- **Docs:** `domain/identity.md` §2.1's `close_round` note says *„Vorbelegt bei `household_admin`
  und `moderator`."*. It is amended in German to „Vorbelegt bei `moderator`", citing `03-PRD.md`
  §4.0.1 and S-50/U-20, in the same step as task 8.3, with a register row. Otherwise a later slice
  would read §2.1 and give the household account `close_round` back (pre-mortem 7). The stale
  comment above the old set in `identity/repository.ts` goes with it.
- **Reads, not only setup:** a test that *reads* on the household context what only a
  `close_round` holder gets (`listOrganisationTasks`, the start bridge) turns into a failing or
  vacuous assertion (`organisation-tasks.test.ts` cases a, b and c). Those reads move to the
  moderator's context, and one explicit test asserts that the household account gets `[]`
  (pre-mortem 5).
- **Teardown:** `createTestModerator` creates a Supabase Auth user. It returns its account id and
  registers it with the household's own cleanup, so `hh.cleanup()` deletes it, or the caller
  deletes it in `afterEach` (pre-mortem 13).

### D4 — `captureApplication(context, input)`: order, locks, errors

It lives in `casting/repository.ts`. The signature takes **no actor**: both actor ids come from
`context` (hazards: *"never from a caller-supplied actor id"*). Steps:

1. `context.profileId === null` → throw `ProfileRequiredError("captureApplication")`, **before any
   query** (G-D15 obligation (a); the RESTRICTIVE policy is the second line).
2. `isUuid(roundId)`, else `ApplicationCaptureError("round_not_found")`.
3. `withSessionContext`, then in **one transaction**:
   - a. `assertHasPermissionTx(tx, context, "create_application")`, exported from
     `identity/repository.ts`. It runs `SELECT … FROM membership WHERE account_id =
     context.accountId AND revoked_at IS NULL FOR SHARE` and refuses (`PermissionDeniedError`) when
     there is no row, when `row.resident_profile_id` ≠ `context.profileId` (a stale session claim),
     or when `membershipHoldsPermission` is false.
   - b. `SELECT id, status FROM casting_round WHERE id = $roundId AND household_id =
     context.householdId FOR SHARE`. No row → `round_not_found`. `status ≠ 'open'` →
     `round_not_open`.
   - c. `parseApplicationInput(input)`, a pure function in a new `casting/application-input.ts`.
     It runs **after** the two checks, so a plain member learns only that the permission is
     missing, whatever it typed (pre-mortem 18). It:
     - trims the name (JavaScript `trim()`) and requires one non-whitespace character;
     - maps an empty optional field to `null`, and drops empty attribute rows; an attribute list
       left empty becomes `null` (assumptions A4);
     - checks every C-3.14 limit in code points;
     - rejects `\u0000` and lone surrogates in every text field (`invalid_characters`), which
       Postgres would otherwise refuse with an encoding error carrying the value (pre-mortem 1);
     - requires `collectedFrom ∈ {data_subject, third_party}`, with no fallback.

     A failure throws `ApplicationInputError { code, field }`, carrying no value. The server
     action may parse first for a quick answer, but the repository never trusts that it did.
   - d. `INSERT application` with `household_id = context.householdId`, `round_id`, `state =
     'new'`, `source = 'manual_form'` (a literal, never from input), `collected_from` from the
     parsed input, the applicant fields, and `created_by_account_id` / `created_by_profile_id`
     from `context`. **The insert is wrapped** (see "No value leaves in an error" below).
   - e. `recordActivityEvent` `application.created`, with `subject_type = 'application'`, both
     actor ids from `context`, and payload `{ source, collectedFrom }`.

**What serializes each read-then-write:**
- *The permission check (a) against a revocation or role change.* `FOR SHARE` on the membership
  row conflicts with every membership writer's row lock (`UPDATE`). A revocation committed first
  is seen, and one in flight is waited for. This closes the window that the two-transaction
  `assertHasPermission` leaves open for the older mutators.
- *The round check (b) against a status change.* `FOR SHARE` conflicts with `openRoundTx`'s
  `FOR UPDATE`, and with any future close or pause. **Obligation, written into the schema
  comment:** every future writer of `casting_round.status` takes `FOR UPDATE` on the row, or the
  pair is no longer serialized.
- *Capture against capture.* Two `FOR SHARE` locks are compatible, and two inserts don't
  conflict. EC-3.1/3.11 want both rows anyway.

**Lock order:** membership, then casting_round. No existing function locks `casting_round` and
then `membership`. `openRoundTx` reads membership without a lock, and
`revokeMembershipForProfileTx` locks no round. So no deadlock cycle exists today. The order is
written in the function's comment for future writers.

**Typed errors**, each with a `code`, following the F2 precedent:
- `ApplicationInputError`: `name_required`, `too_long`, `invalid_age`, `too_many_attributes`,
  `invalid_attribute`, `invalid_characters` or `collected_from_required`, plus a `field`.
- `ApplicationWriteError`: `db_refused`, carrying only the SQLSTATE and the constraint name.
- `ApplicationCaptureError`: `round_not_found`, `round_not_open`.
- The existing `ProfileRequiredError` and `PermissionDeniedError`.

**No value leaves in an error (pre-mortem 1).** Drizzle puts every bound value into a failed
query's message (``Failed query: …\nparams: …``, `node_modules/drizzle-orm/errors.js:12`). Postgres
adds `DETAIL: Failing row contains (…)` in the `cause`, and the Supabase Postgres log keeps it too.
So:
- The capture insert (and the event insert after it) runs inside a `try`. Any error is rethrown as
  `ApplicationWriteError { code: "db_refused", sqlState, constraint }`, built fresh: **no `cause`,
  no `message` from the original, no params.**
- The server action **never logs an error object**. Where the precedent writes `console.error(err)`
  (`rounds/new/actions.ts`), this action logs at most `{ code, sqlState, constraint }`.
- The parser keeps the database from being the one to refuse in the normal case (lengths, blank
  names, `\u0000`, lone surrogates), so a DB refusal is a bug signal, not a user path.
- The Supabase Postgres log is outside the app's control. A CHECK or trigger refusal that reaches
  it logs the row. That is the reason the parser mirrors every CHECK, and a residual risk named in
  Risks.
- A test forces a DB refusal on the insert (the trigger, with a foreign round id passed below the
  repository's check through a test seam, or a CHECK the parser is bypassed for). It asserts that
  neither the thrown error nor anything the action logs contains any of the sentinel values.

*Alternative rejected:* keeping `assertHasPermission` before the transaction, as the room and round
mutators do. It is cheaper by one line, but it leaves a just-removed member able to capture once.
The in-transaction check costs the same number of round trips, because it replaces the separate
membership transaction.

### D5 — `getOrganisationApplication(context, roundId, applicationId)`

The name says which surface this is. It is the **organisation's** read of one application, behind
`/rounds/[id]/applications/[applicationId]` (O5's shell). It is not the read F4's screening deck
will use: there, every participating resident sees the applicant's facts under V-2, through its own
function with its own rule. The two must never be merged into one "application detail" read with
a role switch. That is why this one isn't called `getApplicationDetail`.

This is a read. It returns `null` for a malformed id, an unknown id, a round mismatch or another
household, and throws `PermissionDeniedError` when the permission is missing. Steps:

1. If `profileId === null`, return `null` before any query (the spec: "no database query runs").
2. Check both ids with `isUuid`.
3. Then, in one transaction:
   - `assertHasPermissionTx` with **either** `create_application` or `change_application_state`,
     through a small `assertHoldsAnyPermissionTx(tx, context, [..])` beside it. It is a read, so
     `FOR SHARE` isn't needed for serialization, but reusing the same helper keeps one rule.
   - `SELECT` the application `WHERE id AND round_id AND household_id`.

   The page reads the household name for the notice separately, through `identity`'s exported
   `getHousehold`, never through identity's schema.

The page maps `null` → `notFound()`, and `PermissionDeniedError` → the permission state.

**Sibling reads, checked:**
- `getApplication` (existing) keeps its profile-only check. No `src/app` file calls it. Change 3

### D6 — O3: three quiet steps, client state and the PII rule (human review 2026-09-29)

The first build put every field, the checkbox and the full Art. 14 notice on one page. The human's
review of the walkthrough: *"The whole process should be streamlined and not overstimulating."*
In detail: three contact inputs are clutter; the free text comes first, because the v0.2 parser
will fill the rest from it; and the notice must be *"non invasive & simple … (i) the notice (ii)
a 'understood' button finishing the process and (iii) a button to open the example text to
copy"*. The flow, confirmed by the human against a preview:

| Step | Shows | Buttons |
|---|---|---|
| 1 · Nachricht | the applicant's message (optional), with the code-point counter | „Überspringen", „Weiter" |
| 2 · Angaben | Name* · Alter · **one** „Kontakt" input (with „+ weiteren Kontakt", at most 3) · „+ Weitere Angaben" (collapsed until used) · the statement „Angaben von der bewerbenden Person" and the checkbox | „Zurück" and „Speichern", or „Weiter" instead of „Speichern" when the box is ticked |

- **„Verstanden" saves.** So the notice is still displayed before saving (AC-3.8, O3 „noch vor dem
  Speichern", R-3.2 duty and text in the same step), and it adds no extra click. Step 2's
  „Speichern" saves for the applicant as source. Both use the one server action, and both land on
  the **round** with the toast „Bewerbung gespeichert". The text was offered in step 3, and the
  application's detail keeps it for later (FR-3.12, „afterwards").
- **Validation per step, in the browser, for speed only**: step 2 blocks an empty name and marks

  holding the named field (the message → step 1, anything else → step 2), with every value intact
  and the error beside that field.
- **The notice (step 3), non-invasive.** It uses the neutral **info** style (`callout-info`), not
  the caution style, with no red and no bold beyond the date, and exactly two lines:
  - „Die Person muss erfahren, dass ihr ihre Angaben gespeichert habt."
  - the Compliance §4.5 line, verbatim: *„Am besten gleich mit deiner ersten Nachricht an {Name}

  Together they state both deadlines of FR-3.11: the first message, and the one-month date.

### D15 — One contact input, sorted into the three stored columns (human review 2026-09-29)

The schema keeps `contact_email`, `contact_phone` and `contact_other` (`domain/casting.md` §2.2,
Compliance §6.2: the email doubles as identity proof in a subject request, so it must stay
findable as an email). Only the form changes. Each „Kontakt" input is sorted by one pure,
deterministic function in `casting/application-input.ts`, `classifyContact(value)`. It is used by
the parser (server) and by the form's hint (browser), and applied in this order:

1. **email**: no whitespace, exactly one `@`, at least one character before it, and a dot inside
   the part after it. Goes to `contact_email` (≤ 254).
2. **phone**: only digits, spaces and `+ ( ) - / .`, with at least 6 digits. Goes to
   `contact_phone` (≤ 50).
3. **anything else** goes to `contact_other` (≤ 200): a portal handle, a messenger id.

This is P-3 explainable: a fixed rule that the screen names for each input, with no guessing model
(P-5 untouched). The parser takes `contacts: string[]`: at most 3, blanks dropped, each trimmed and
classified. Two contacts landing on the same kind are refused (`contact_kind_taken`, field
`contact`), because each column holds one value. The screen then names the input that clashes.
`readOptionalText`'s limits apply per column after sorting, and too long means `too_long` with
field `contact`. The explicit `contactEmail`/`contactPhone`/`contactOther` inputs of the first
build go away. The seed and the tests pass `contacts` instead.

that needs one is either run on a local or CI disposable stack, or **argued in the test's comment**
(the `raw-sql/membership-resident-pairing.test.ts` precedent, "argued, not executed"). The report
says which, and never claims a break was run when it was argued (pre-mortem 8).

open (wave 2 runs alone). After applying, the applier checks the catalog, the columns, NOT NULL,
no default, each CHECK and the pairing trigger, and **stops if any is missing**. CI's `verify` builds from `drizzle/`

### D12 — `application.round_id` must name a round of the same household, enforced by a trigger

**The relationship.** A captured application pairs `household_id` with `round_id`. The repository
guarantees the pairing (D4 b), but raw SQL as `app_runtime` could store any uuid in `round_id`,
since there are no foreign keys. That is no cross-household read today: RLS on `application`
filters on its own `household_id`, and `WITH CHECK` forbids writing another household's id. Two
things read *through* the pairing, though:
- the retention slice anchors `retention_until` on that round's `closed_at`, so a misfiled row
  would be deleted on the wrong schedule or never (storage limitation);
- change 6's V-2 policy joins `round_participation` on `application.round_id`.

The hazards rule applies: *"If it isn't [a constraint], add the constraint once rather than a
predicate in every reader."* The table is empty now, so this is the cheap moment.

**Shape.** A plpgsql trigger function, **not `SECURITY DEFINER`** (so there is no harness refusal
and no `definer-coverage` obligation), with `SET search_path = pg_catalog, public`:

```sql
IF NEW.round_id IS NULL THEN RETURN NEW; END IF;
IF NOT EXISTS (SELECT 1 FROM casting_round
               WHERE id = NEW.round_id AND household_id = NEW.household_id) THEN
  RAISE EXCEPTION 'application.round_id must name a round of the same household'
    USING ERRCODE = '23503', CONSTRAINT = 'application_round_same_household';
END IF;
RETURN NEW;
```

The explicit `household_id = NEW.household_id` predicate carries the rule. RLS is only an extra
layer: running as the writer, the lookup also cannot see another household's rounds. As `postgres`
(the SQL editor, the migrations) RLS is bypassed and the predicate alone still decides. The
trigger fires on `INSERT` and on `UPDATE OF round_id, household_id`. Nothing updates either column
today, and change 3's edit must not make `round_id` editable. The other side of the pair: no path
deletes a `casting_round` or changes its `household_id`. If one ever does, it has to consider the
applications pointing at it. Written into the `castingRound` schema comment.

**Error mapping.** `captureApplication` never reaches the trigger's refusal, because D4 b refuses
first with `round_not_found`. If the trigger ever fires from the repository, that is a bug and
surfaces as an internal error, not as a mapped code.

**Cost for tests.** Every direct insert needs a real round of the same household. D8's
`insertTestRound` provides it. Six of the seven existing insert sites set no `roundId` today; only
`start-overview` does (pre-mortem 16).

**NULL round:** the function starts with `IF NEW.round_id IS NULL THEN RETURN NEW; END IF;`, so a
missing `round_id` is refused by NOT NULL (`23502`), as the spec says, instead of by the trigger
(pre-mortem 2).

*Alternative rejected:* a composite foreign key `(round_id, household_id) → casting_round(id,
household_id)`. It is stronger, but it would be the schema's first foreign key against a
deliberate no-FK design, and that is a human decision outside this change.

## Risks / Trade-offs

- **The older mutators keep the permission/write window.** They are `createRoom` etc., with
  `assertHasPermission` in a separate transaction. D4 closes it only for capture. → Recorded in
  `review-log.md` §Implementierungspflichten as a sweep for a later change. Not widened here.
- **The attribute element limits are not in the DB.** → Named in the schema comment and the spec.
  The repository is the only writer, and a raw-SQL writer could store long attribute values; the
  array length is still bounded.
- **Every other branch breaks on dev the moment 0023/0024 are applied**, not only its application
  inserts. `main`'s `registerHousehold` stores `permissions: []` for the household account, which
  0024's exact-set CHECK refuses. So every `registerTestHousehold`, `seed:demo` and pre-push hook
  on another branch fails against dev until this merges (pre-mortem 6). → Apply late (D11), merge
  promptly, and tell the human before applying. `verify-hosted` on `main` fails between the apply
  and the merge.
- **The Supabase Postgres log records a refused row.** → The parser mirrors every CHECK, so only a
  bug reaches the database's refusal (D4).
- **The client-side notice text and the server's categories could drift** (the detail page
  computes from stored fields, O3 from inputs). → Both call the same `noticeCategories`. A unit
  test covers both inputs.
- **A month "clamped to the month end" is a legal reading, not a statute quote.** → A2 records it.
  The text says „spätestens bis", so erring early is safe.
- **`deleted_at` survives this change and a future read could forget it.** → No new read filters
  or writes it, and change 4 drops it.
